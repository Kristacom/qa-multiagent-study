## 1. Введение и назначение
Сервис `booking-service` (Restful-Booker API) предназначен для автоматизации управления бронированиями в гостиничном бизнесе. Предоставляет публичный REST API для создания бронирования, получения информации о гостях, валидации дат заезда/выезда и аутентификации администраторов для защищенных операций.

Версия 4.0 устраняет все ранее зафиксированные неоднозначности (DISC-01..DISC-10), строго фиксирует контракты ответов и ошибок для всех методов и утверждает единый источник истины.

## 2. Функциональные требования (Functional Requirements)

### FR-01: Создание нового бронирования (Create Booking)
- **Метод и Эндпоинт:** `POST /booking`
- **Заголовки:** `Content-Type: application/json`, `Accept: application/json`
- **Обязательные поля тела запроса:**
  - `firstname`: строка (имя гостя)
  - `lastname`: строка (фамилия гостя)
  - `totalprice`: целое положительное число (> 0)
  - `depositpaid`: boolean (внесен ли депозит)
  - `bookingdates`: объект, содержащий `checkin` (YYYY-MM-DD) и `checkout` (YYYY-MM-DD)
  - `additionalneeds`: строка (дополнительные пожелания, опционально)
- **Успешный ответ:** **HTTP 200 OK** с телом `{"bookingid": 1, "booking": {...}}`.
- **Контракт ошибок:**
  - При отсутствии обязательных полей или невалидном формате даты (не ISO 8601 YYYY-MM-DD) сервер возвращает **HTTP 400 Bad Request** с телом `{"error": "Bad Request", "message": "Missing required booking fields or invalid date format"}`.
  - При заголовке, отличном от `application/json`, возвращается **HTTP 415 Unsupported Media Type**.

### FR-02: Получение деталей бронирования (Get Booking by ID)
- **Метод и Эндпоинт:** `GET /booking/{id}`
- **Заголовок:** `Accept: application/json`
- **Успешный ответ:** **HTTP 200 OK** с JSON-телом бронирования при существующем ID.
- **Контракт ошибок:** **HTTP 404 Not Found**, если бронирование с данным `id` не существует или было ранее удалено.

### FR-03: Аутентификация администратора (Admin Auth)
- **Метод и Эндпоинт:** `POST /auth`
- **Заголовки:** `Content-Type: application/json`
- **Успешный ответ:** При теле `{"username": "admin", "password": "password123"}` сервер возвращает **HTTP 200 OK** с токеном: `{"token": "<alphanumeric_16>"}`. Срок жизни токена (TTL) составляет ровно **600 секунд (10 минут)**.
- **Контракт ошибок:**
  - При любых неверных учетных данных возвращается **HTTP 401 Unauthorized** с телом `{"error": "Unauthorized", "message": "Bad credentials"}`.
  - При превышении лимита в 5 попыток авторизации в минуту возвращается **HTTP 429 Too Many Requests**.

### FR-04: Модификация и удаление брони (Update, Partial Update & Delete)
- **Методы и Эндпоинты:**
  - `PUT /booking/{id}`: полное обновление всех полей бронирования.
  - `PATCH /booking/{id}`: частичное обновление подмножества переданных полей.
  - `DELETE /booking/{id}`: аннулирование (удаление) бронирования.
- **Авторизация:** для всех трех методов обязателен заголовок `Cookie: token={token}` с активным токеном администратора.
- **Успешный ответ:**
  - `PUT` и `PATCH` возвращают **HTTP 200 OK** с обновленным объектом бронирования.
  - `DELETE` возвращает **HTTP 201 Created** (или HTTP 200 OK).
- **Контракт ошибок:**
  - При отсутствии или истечении токена возвращается **HTTP 403 Forbidden**.
  - Повторный вызов `DELETE` по уже удаленному идентификатору возвращает **HTTP 405 Method Not Allowed** или **HTTP 404 Not Found** (гарантия идемпотентности).

## 3. Бизнес-правила (Business Rules)
- **BR-01 (Валидация дат):** Дата выезда (`checkout`) должна быть строго позже даты заезда (`checkin`). Формат: строго `YYYY-MM-DD`. Если `checkout <= checkin`, возвращается **HTTP 400 Bad Request**.
- **BR-02 (Ограничение стоимости):** Поле `totalprice` должно быть положительным числом (> 0). При `totalprice <= 0` возвращается **HTTP 400 Bad Request**.
- **BR-03 (Защита модификаций):** Операции изменения и удаления требуют активного токена с проверкой срока его жизни (TTL 600c).

---

## 4. Нефункциональные требования (NFR)
- **NFR-01 (SLA & Latency):** Время отклика API на 95-м перцентиле не более **600 мс** для всех методов.
- **NFR-02 (Data Format):** Строгий обмен в формате `application/json`.
- **NFR-03 (Rate Limiting & Security):** Защита эндпоинта `POST /auth` от перебора паролей (не более 5 запросов в минуту).
